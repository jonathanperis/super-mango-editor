# PRODUCT.md

## Product Identity

Super Mango is an open-source 2D side-scrolling pixel platformer and a learning
project, written in C11 with raylib. It runs natively on macOS, Linux and
Windows, and the website plays a WebAssembly build of it.

The website is where most people meet it. It should let someone play within a
few seconds, then show them how the game is made: the manual, the source, the
level editor and the lessons. The home page itself is built from the game: a
small level drawn with the real sprites, the start-menu logo as the title, and
the playable canvas a scroll below. [DESIGN.md](DESIGN.md) describes how it
looks.

## Primary Users

### Browser players

People who arrive from GitHub, social links, or a search result and want to try the game immediately. They are curious, impatient, and deciding within seconds whether the page is playable or only documentation.

### C and raylib learners

Developers who want a readable game codebase with real systems: input, game loop, collision, rendering, audio, assets, WebAssembly build, and level loading. They need proof that the project is approachable and well documented.

### Level builders and modders

Users who care about the visual editor, TOML level format, assets, and creating or modifying levels. They need a path from playing to understanding how levels are built.

### Open-source reviewers and contributors

Developers checking project quality before cloning, starring, filing issues, or contributing. They look for build clarity, CI confidence, source organization, and documentation depth.

## User State of Mind

People arrive curious and short on time. A player wants to know whether the
page is a game they can try right now; a learner wants to know whether the
code is something they can actually follow. The page should answer both with
the game itself and plain, specific text, and then get out of the way.

## Core Value Propositions

1. **Play instantly in the browser.** The website hosts the WebAssembly build and loads the game into an embedded canvas.
2. **Learn from a real C11 and raylib game.** The project is positioned as an educational resource with commented code and architecture docs.
3. **Build and inspect levels.** Levels are TOML data files, and the repo includes a standalone visual level editor.
4. **Study a complete platformer stack.** The codebase includes rendering layers, physics, collision, enemies, hazards, pickups, overlays, audio, and native/WebAssembly builds.
5. **Run anywhere.** The project targets Linux, macOS, Windows, and browser play.

## Canonical Product Facts

Current numeric facts come from `docs/src/generated/project.json`, generated by
`make content-inventory`. The [Level Catalog](docs/wiki/level-catalog.md) and
[Asset Inventory](docs/wiki/asset-inventory.md) contain the corresponding detail.
The project now includes Sandbox School, focused mechanics levels and an opt-in
simulation inspector with reproducible experiment capture.

Source-backed facts for design and copy:

- Language and stack: C11, pinned raylib 6.2, vendored tomlc17, Emscripten/WebAssembly.
- Rendering: 400x300 logical resolution scaled to an 800x600 native window for chunky pixel rendering.
- Browser payload callout: generated raw playable-asset size plus engine overhead; not an unmeasured compressed-transfer claim.
- Campaign: the ordered v1 `levels/campaigns/main.toml`; separate focused examples live in `levels/labs/`.
- Campaign names: Creator's Playground, Volcanic Depths 1, Volcanic Depths 2.
- Gameplay systems: one-way platforms, floating platforms, crumble bridges, floor gaps, animated water/lava, authored checkpoints, bouncepads, vines, ladders, ropes, coins, stars, hearts, lives, score, pause, game over, completion flow.
- Enemy set: spiders, jumping spiders, birds, faster birds, fish, faster fish.
- Hazard set: spike rows, spike blocks, spike platforms, circular saws, axe traps, blue flames, fire flames.
- Visual systems: parallax backgrounds, 33 render layers, scrolling camera, fog overlays, HUD, debug overlay.
- Level editor: standalone raylib editor with canvas, checkpoint-aware palette and markers, select/place/delete tools, properties inspector, level config, undo/redo, recent files, autosave, validation, TOML save/load, and play-test integration.
- Controls: the site's control strip shows WASD or arrows to move and Space to jump (W/S climb); on-screen touch buttons sit below the browser canvas. Docs also describe gamepad hot-plug support and F1 remapping.
- Authors: Jonathan Peris and Fernando Santos.
- Art credit: Super Mango 2D Pixel Art Platformer Asset Pack by Juho.

## Voice

I write in the first person, plainly, and about specific things: what the game
is, why I wrote it, what you can learn from it, and what a button does. The
same voice runs through the website, the manual, this file and the README.

- Say what is there and where to find it, with a file, a command or a number
  the repository can back up.
- Keep labels plain ("Play in the browser", "Open the manual", "Take it home").
  No console or status-panel jargon, no fake system labels, no hype.
- A playful line is fine when the sentence still says something exact.

Avoid:

- Generic marketing language such as "seamless", "powerful", "beautiful", "next generation", or "unlock your creativity".
- Unsupported claims about speed, polish, or production readiness.
- Copy that makes the game sound like a SaaS product.

## Current Look

The site's look is set out in [DESIGN.md](DESIGN.md): real sprites and the
game's own 9-slice ground, game-style text boxes with thick black edges and
solid offset shadows instead of glows, a palette taken from the art (night
blues, leaf green and mango red from the logo, coin gold for actions),
Pixelify Sans for headings and buttons, Atkinson Hyperlegible for reading and
DM Mono for code. The manual shares the same tokens.

## Success Metrics

For the sandbox-school goal, what matters is a successful first build, a first
edit and playtest, finding the source of a behaviour, finishing the entity
lab, and a reproducible experiment with an explanation. Optional analytics
loads only on manual (`/docs/`) pages, never on the home page that hosts the
game.

## Non-Goals

- Do not redesign the site into a generic tech landing page.
- Do not move the playable game off the home page.
- Do not hide the educational/codebase promise behind only game marketing.
- Do not add unsourced claims or fake social proof.
- Do not implement broad visual changes inside context-documentation commits.
